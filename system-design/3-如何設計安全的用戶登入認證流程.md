# 如何設計安全的用戶登入認證流程

認證要回答「**這個請求是誰**」；授權才回答「**能不能做這件事**」。常見取捨：**Access Token 短期 + 放記憶體 / Authorization header；Refresh Token 長期 + HttpOnly Cookie + 伺服器可撤銷** — 偷到 access 窗口小，refresh 不進 JS，登出與異常仍可作廢 session。

### 本質一：為什麼要雙 Token

- **問題**：單一長效 JWT 被偷 = 長時間冒充；全放 Cookie 又讓 CSRF 面變大；全放 localStorage 又讓 XSS 可讀。
- **Access Token（短，如 15m–1h）**：每次 API 帶 `Authorization: Bearer …`；過期快，**洩漏損害面小**。
- **Refresh Token（長，如 7–30d）**：**只**走 `POST /auth/refresh`；存 **HttpOnly + Secure + SameSite** Cookie，JS 讀不到。
- **機制**：日常請求驗 access；access 過期用 refresh **靜默換新**，使用者少重登。
- **誤解**：Refresh 也是 JWT 就夠 — 若不在 DB / session store **登記與撤銷**，登出與「踢全裝置」做不到。

### 本質二：四段流程（因果順序）

**1. Login**

- 後端：查 user → **bcrypt** 比對密碼 → 簽 access + refresh → **refresh 寫 DB**（userId、expires、revoked）→ `Set-Cookie` refresh → body 回 access + 公開 user 欄位。
- 前端：access 存 **記憶體變數**（或 closure）；**不要** localStorage。Refresh 由瀏覽器自動帶 Cookie。
- 錯誤回應：登入失敗統一 `Invalid credentials`，勿區分「email 不存在 / 密碼錯」。

**2. 存取受保護資源**

- 前端：`Authorization: Bearer ${accessToken}`。
- 後端 middleware：`jwt.verify(access)` → 掛 `req.user` → **業務路由仍要查授權**（role、資源 owner），不能只看「有 token」。

**3. Refresh（access 過期）**

- 觸發：API 回 **401 + `TOKEN_EXPIRED`**（或統一 401 後前端判斷）。
- 前端：`fetch('/auth/refresh', { method: 'POST', credentials: 'include' })` → 新 access → **重試原請求**；refresh 失敗 → 清 memory、導向 login。
- 後端：讀 Cookie refresh → verify → **查 DB 未 revoked 且未過期** → 簽新 access → **建議 rotation**：作廢舊 refresh、發新 refresh 再 Set-Cookie。
- **Rotation 為什麼**：舊 refresh 被重放可偵測（DB 已撤銷）→ 可視為盜用信號。

**4. Logout**

- 前端：清 memory access；`POST /logout` + `credentials: 'include'`。
- 後端：DB **revoke** 該 refresh（或刪 row）→ `clearCookie` → 可選撤銷該 user 全部 refresh（改密、封號）。

### 本質三：Token 存哪裡 — 威脅對照

| Token | 推薦 | 避免 | 被偷後果 |
|-------|------|------|----------|
| Access | 記憶體；或 Bearer only | localStorage | XSS 可讀 → 短期 API 濫用 |
| Refresh | HttpOnly Cookie | JS 可讀 storage | XSS 可長期換 access |

- **CSRF 與 refresh**：SameSite `Strict`/`Lax` 限制跨站帶 Cookie；若 refresh 僅 Cookie、access 在 header，簡單 CSRF 表單較難直接打 API，但 **state-changing 仍建議 CSRF token**（見 `web/2-web-security-practices.md`）。
- **HTTPS**：`Secure` Cookie 與 token 傳輸必須。

### 本質四：伺服器端必備能力

- **Refresh 持久化**：登入寫入、refresh 驗證查表、logout / rotation / 管理員踢人 **mark revoked**。
- **雙 secret**：access / refresh 用不同 `JWT_SECRET`，一個洩漏不拖垮另一個。
- **Payload 最小化**：access 帶 `userId`、`role` 等驗證所需即可；勿塞 PII。
- **多裝置**：每裝置一條 refresh record（device id），可單獨撤銷。
- **前端封裝**：統一 `apiRequest` 處理 401 → refresh → retry，避免每個 fetch 複製邏輯。

### 本質五：認證 ≠ 授權

- Middleware 只完成 **Authentication**。
- **Authorization** 在每個 handler：`user.role === 'admin'`、訂單 `order.userId === req.user.id` 等 — UI 藏按鈕不算安全。
- **誤解後果**：「有 JWT 就安全」→ 水平越權（改 URL 看別人資料）。

### 常見陷阱

- **Refresh 純 stateless JWT、不存 DB** — 無法登出生效、無法 rotation 偵測重放。
- **Access 放 localStorage「方便」** — 一個 XSS 全拿。
- **Refresh 不 rotation** — 被偷 refresh 可用到過期。
- **401 訊息過細** — 協助枚舉帳號或 token 狀態。
- **只驗證 token 不驗證 user 仍有效** — 後端已刪 user / 封禁，JWT 未過期仍通過。

### 與 Web 安全筆記的關係

- **`web/2-web-security-practices.md`**：XSS / CSRF / CSP / 輸入驗證 **威脅模型**；本篇是 **登入態怎麼發、怎麼存、怎麼刷新、怎麼撤銷** 的具體流程。
- 分工：安全筆記講防線種類；本篇講 Access + Refresh 雙 token 架構如何對應那些威脅。

### 小結

- **問題**：既要 UX（少重登）、又要 stolen token 損害可控、且能登出與踢人。
- **手段**：短 access + 長 refresh（HttpOnly Cookie + DB 可撤銷）+ rotation + 記憶體存 access + middleware 驗證 + 業務層授權。
- **結果**：API 用 Bearer 無狀態擴展；session 生命週期仍由伺服器 refresh 表掌控。
